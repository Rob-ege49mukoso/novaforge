# Mémoire durable

- Produit : NovaForge — plateforme IA universelle (FR) qui transforme une idée en application, API ou agent IA fonctionnel ; version 1.4.0 livrée (plan v1.4 terminé). [tags: produit, version]
- Stack imposée : Node.js 20+, zéro dépendance npm, serveur `server/app.js` + front statique `public/`, tests via `node --test`. [tags: stack, contrainte]
- Principe produit non négociable : aucun statut connecté ou actif sans test réel réussi, aucune transaction simulée, le code produit est testé avant d'être annoncé fonctionnel. [tags: principe, honnêteté]
- La commande shell dans l'automatisation reste désactivée tant qu'un exécuteur isolé n'existe pas ; ne pas la réactiver. [tags: sécurité, automatisation]
- v1.4 étape 1 livrée : boucle d'outils (`runToolLoop` dans server/lib/llm.js, garde-fous anti-boucle + trace `tools_used`), moteur local NovaCore dans server/lib/novacore.js (les agents sans fournisseur IA utilisent la même boucle d'outils), streaming SSE sur les deux endpoints de chat (mode JSON historique conservé), UI avec indicateur de saisie et bouton d'arrêt. [tags: v1.4, streaming, outils]
- Plan v1.4 terminé : (1) boucle d'outils + streaming assistant/agents — LIVRÉ, (2) passerelle de paiement automatisée Candy/Flutterwave — LIVRÉ, (3) épinglage d'IP anti-DNS-rebinding dans server/lib/network.js — LIVRÉ, (4) tests élargis + documentation v1.4 — LIVRÉ. [tags: plan, develop]
- Suite de tests automatisés de NovaForge : 79 tests (`node --test`, zéro dépendance npm, tout en français) répartis en 10 fichiers — `security`, `resources`, `llm-tools`, `chat-stream` (étapes 1), `payments` (étape 2), `network` (étape 3), `auth`, `quotas-billing`, `generator`, `automation` (étape 4). Les tests HTTP démarrent le serveur réel sur un port libre avec repli si le port est pris (exécution en parallèle possible). Ne pas réécrire les étapes 1 à 3 : elles doivent rester vertes. [tags: tests, v1.4]
- v1.4 étape 3 livrée : durcissement SSRF dans `server/lib/network.js` — nouveau client `requestOutbound()` : une seule résolution DNS, validation de TOUTES les adresses, connexion à l'adresse validée via un `lookup` personnalisé (`node:http`/`node:https`, zéro dépendance npm), nom d'hôte conservé pour l'en-tête Host, le SNI et la vérification du certificat (non désactivée), redirections suivies mais re-résolues et re-validées à chaque saut, IPv6 et IPv4 mappées (`::ffff:`, NAT64) contrôlées via les règles IPv4. Appliqué aux fournisseurs IA (dont le SSE), MCP, automatisations, passerelle de paiement et outil `web_fetch` des agents ; `readLimited` accepte les flux Node comme les flux web. Limites SSRF obsolètes retirées de SECURITY_NOTES. [tags: v1.4, ssrf, réseau]
- v1.4 étape 2 livrée : passerelle de paiement automatisée dans `server/lib/payments.js` (adaptateur Flutterwave sur contrat officiel documenté + adaptateur générique « Candy » entièrement décrit par le Super Admin, aucun endpoint inventé), statut « active » uniquement après test de connexion réel réussi, secrets jamais renvoyés en clair (empreinte masquée), webhook signé (plain type « verif-hash » ou HMAC-SHA256 hex/base64) idempotent, contrôle du montant et de la devise, activation automatique de l'offre 30 jours, flux mobile money manuel et commission 10 % préservés, routes admin + onglet « Passerelle » dans l'interface. [tags: v1.4, paiement, sécurité]
